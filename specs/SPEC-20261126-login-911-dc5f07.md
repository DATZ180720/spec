# login 911
## 1. Contexto y problema

El proyecto requiere implementar un mecanismo de autenticación robusto que permita a los usuarios iniciar sesión y registrarse de manera segura, garantizando la protección de credenciales, la prevención de ataques comunes y la conformidad con las mejores prácticas de seguridad. Este login debe incluir todas las medidas de seguridad estándar, como hashing de contraseñas, verificación por correo electrónico, protección CSRF, limitación de intentos y soporte opcional de autenticación de dos factores.

## 2. Objetivos y no objetivos

**Objetivos**

- Implementar autenticación segura
- Facilitar registro de usuarios
- Garantizar cumplimiento de normativas de seguridad

**No objetivos**

- No se implementará autenticación social
- No se incluirá gestión de roles compleja

## 3. Requisitos funcionales

- **RF-1** El sistema debe permitir a un usuario registrarse con correo electrónico y contraseña, validando el formato del correo y la complejidad de la contraseña.
- **RF-2** El sistema debe enviar un correo de verificación con un enlace único y expiración de 24h para activar la cuenta.
- **RF-3** El sistema debe permitir a un usuario iniciar sesión con correo y contraseña, verificando credenciales y generando una sesión segura.
- **RF-4** El sistema debe limitar los intentos de inicio de sesión a 5 por IP en 15 minutos para prevenir ataques de fuerza bruta.
- **RF-5** El sistema debe proteger las rutas sensibles contra CSRF mediante tokens.
- **RF-6** El sistema debe permitir la recuperación de contraseña mediante un enlace seguro de un solo uso.
- **RF-7** El sistema debe soportar autenticación de dos factores (2FA) mediante OTP por correo o SMS, opcional.

## 4. Requisitos no funcionales

| ID | Requisito | Meta |
|---|---|---|
| RNF-1 | El tiempo de respuesta del login no debe superar 2 segundos bajo carga normal. | ≤2s |
| RNF-2 | El sistema debe cumplir con OWASP Top 10 de seguridad. | Cumplimiento |
| RNF-3 | La disponibilidad del servicio de autenticación debe ser ≥99.9%. | ≥99.9% |

## 5. Diseño propuesto y decisiones

La arquitectura propuesta incluye una capa de presentación (frontend) que interactúa con una API RESTful en el backend. El backend está construido sobre Node.js con Express, utilizando JWT para la autenticación de API y cookies de sesión para la web. Los datos de usuario se almacenan en PostgreSQL, mientras que Redis se emplea para almacenar tokens de verificación, bloqueo de IP y sesiones temporales. El flujo de registro incluye validación de correo, hash de contraseña con bcrypt (coste 12), envío de correo de verificación y activación de cuenta. El flujo de login verifica credenciales, genera una cookie HttpOnly Secure SameSite=Lax y, si 2FA está habilitado, solicita OTP. Se implementan mecanismos de rate limiting y protección CSRF con tokens generados por la librería csurf.

### Decisiones

| Decisión | Elegido | Descartado | Razón |
|---|---|---|---|
| Método de autenticación | Cookies de sesión | JWT | Mayor control de revocación y mitigación de XSS |
| Algoritmo de hashing de contraseñas | bcrypt 12 | argon2 | Compatibilidad y rendimiento aceptable |
| Canal de verificación de cuenta | Correo electrónico | SMS | Costo y cobertura |
| Almacenamiento de tokens y bloqueo IP | Redis | Memcached | Persistencia y TTL |

## 6. Contratos (API / datos)

Feature: Implementación de login y registro seguro con todas las medidas de seguridad estándar.

## 7. Criterios de aceptación

- **CA-1** (RF-1) **Dado** Un usuario con correo válido y contraseña compleja, **cuando** Intenta registrarse, **entonces** Se crea la cuenta y se envía correo de verificación.
- **CA-2** (RF-2) **Dado** Una cuenta recién creada, **cuando** El usuario hace clic en el enlace de verificación, **entonces** La cuenta se activa.
- **CA-3** (RF-3) **Dado** Una cuenta activa, **cuando** El usuario ingresa credenciales correctas, **entonces** Se inicia sesión y se establece cookie de sesión.
- **CA-4** (RF-4) **Dado** 5 intentos fallidos desde la misma IP, **cuando** Se intenta un sexto intento, **entonces** Se bloquea la IP por 15 minutos.
- **CA-5** (RF-5) **Dado** Una solicitud a ruta protegida, **cuando** Se omite token CSRF, **entonces** La solicitud es rechazada con 403.
- **CA-6** (RF-6) **Dado** Una cuenta con correo registrado, **cuando** Solicita recuperación de contraseña, **entonces** Se envía enlace de un solo uso.
- **CA-7** (RF-7) **Dado** Una cuenta con 2FA habilitada, **cuando** Inicia sesión, **entonces** Se solicita OTP y se valida.

## 8. Plan de pruebas

El plan de pruebas incluye: pruebas unitarias para hashing y validación de correo; pruebas de integración para registro, verificación, login y recuperación de contraseña; pruebas de seguridad para CSRF, rate limiting y XSS; pruebas de rendimiento para asegurar ≤2s de respuesta; pruebas de disponibilidad con simulación de carga y failover de Redis.

## 9. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Almacenamiento de contraseñas | Usar bcrypt 12, salting, no almacenar en texto plano. |
| Ataques de fuerza bruta | Limitar intentos, bloqueo IP, CAPTCHA opcional. |
| Phishing de correo de verificación | Enlazar a dominio seguro, usar enlaces únicos y expirables. |
| Exposición de cookies | Set HttpOnly, Secure, SameSite=Lax. |
| Dependencia de servicio de correo | Implementar fallback y monitorización. |
